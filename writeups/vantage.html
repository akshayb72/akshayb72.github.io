Vantage

HTB DFIR Sherlocks Very Easy Vantage Jun 2026
01 / overview

What We're Given

Vantage is an HTB Sherlocks DFIR challenge. We're given two packet captures: controller.xxx.pcap and webserver.xxx.pcap. The scenario is a mall company moved some of its resources to a private cloud installation. The developers left the redirect to the dashboard on their web server. The security team got an email from the alleged attacker stating that the user data was leaked. It is up to you to investigate the situation.. The goal is to trace the attacker from initial recon through to persistence.

Environment layout Two captures = two vantage points. The webserver pcap shows what hit the public-facing dashboard. The controller pcap shows the attacker talking directly to the OpenStack REST APIs once they had credentials.
02 / webserver-pcap

Identifying the Fuzzing Tool

Open webserver.xxx.pcap and use the filter http in wireshark.Then go through the packets and in packet 116, I see something interesting.Expand the HTTP layer for the packet and the User-Agent header gives the tool and its version immediately. 

frame.number == 116
GET / HTTP/1.1
Host: dev.vantage.tech
User-Agent: Fuzz Faster U Fool v2.1.0-dev
Accept-Encoding: gzip

Task 1 — What tool did the attacker use to fuzz the web server? (include version)

ffuf@2.1.0
03 / subdomain

Finding the Discovered Subdomain

Since ffuf was fuzzing for subdomains, we want the hits — responses that came back 200 OK rather than 404. Filter for HTTP 200 responses destined for the attacker's IP: 

Filter: ip.dst == 117.200.21.26 && _ws.col.info == "HTTP/1.1 200 OK  (text/html)"
Many results — most have frame.len == 596 (the baseline fuzz response)

Most results share the same length of 596 — that's the generic response ffuf gets back for non-existent subdomains. Excluding that length isolates the real hits: 

Refine: ip.dst == 117.200.21.26 && _ws.col.info == "HTTP/1.1 200 OK  (text/html)" && frame.len != 596
Down to 12 packets — all hitting http://cloud.vantage.tech
Host: cloud.vantage.tech

Task 2 — Which subdomain did the attacker discover?

cloud
04 / dashboard-login

Brute-Forcing the Dashboard

With cloud.vantage.tech found, the attacker targeted the Horizon login page. Filter the webserver pcap for POST requests to the auth path: 

Filter: http.request.method == "POST" && http.request.uri contains "auth/login"
Pkt 20822 — POST /dashboard/auth/login/  →  302 Found  (fail)
Pkt 20827 — POST /dashboard/auth/login/  →  302 Found  (fail)
Pkt 21091 — POST /dashboard/auth/login/  →  302 Found  (fail)
Pkt 21098 — POST /dashboard/auth/login/  →  200 OK     (success)

Four total attempts. The first three redirect back to the login page (failed auth). The fourth returns 200 — the attacker is in.

Task 3 — How many login attempts did the attacker make before successfully logging in?

3
05 / openrc-download

OpenStack RC File Download

Once inside the dashboard, the attacker grabbed the OpenStack RC file — the credential bundle that enables API access from the command line. Go to File → Export Objects → HTTP, sort by size descending, and scroll until two entries named openrc appear (packets 21256 and 21260). Check both: one originates from the internal network, the other from the attacker's IP (117.200.21.26). That's packet 21260. 

Packet 21260 — HTTP response headers
HTTP/1.1 200 OK
Date: Tue, 01 Jul 2025 09:40:29 GMT
Content-Disposition: attachment; filename="admin-openrc.sh"
Content-Type: text/plain

Task 4 — When did the attacker download the OpenStack API remote access config file? (UTC)

2025-07-01 09:40:29
06 / controller-pcap

First Contact with the Controller API

Switch to controller.xxx.pcap. Filter by the attacker's source IP and HTTP to isolate their API calls: 

Filter: ip.src == 117.200.21.26 && http
First matching packet: 8490
GET /identity HTTP/1.1  →  134.209.71.220

Expand the frame details on packet 8490 and read the UTC Arrival Time field.

Task 5 — When did the attacker first interact with the API on the controller node? (UTC)

2025-07-01 09:41:44

The attacker then queried Keystone for the default project. Filter for projects in the URI — six packets appear. Packets 20710 and 23129 relate to the default project. Follow packet 20710 as an HTTP stream to read the project ID from the JSON response. 

Filter: ip.src == 117.200.21.26 && http.request.uri contains "projects"
6 packets — focus on 20710 and 23129 for the default project
Follow HTTP stream on packet 20710...
{"id": "9fb84977ff7c4a0baf0d5dbb57e235c7", "name": "admin", "domain_id": "default", ...}

Task 6 — What is the project ID of the default project accessed by the attacker?

9fb84977ff7c4a0baf0d5dbb57e235c7

Task 7 — Which OpenStack service provides authentication and authorization for the OpenStack API?

keystone
The /identity/v3/ path visible throughout the controller pcap is the Keystone API endpoint. Any time you see OpenStack, auth goes through Keystone — worth remembering for future cloud DFIR work.
07 / swift

Object Storage Enumeration

The attacker moved to Swift — OpenStack's object storage service (similar to S3). Looking up the Swift endpoint structure reveals the pattern http://<ip>:8080/v1/AUTH_<project_id>. With the project ID already known, we can construct the URL and confirm it in the pcap. 

Filter: ip.dst == 134.209.71.220 && http.request.uri contains "v1"
GET /v1/AUTH_9fb84977ff7c4a0baf0d5dbb57e235c7?format=json HTTP/1.1
Host: 134.209.71.220:8080

Task 8 — What is the endpoint URL of the Swift service?

http://134.209.71.220:8080/v1/AUTH_9fb84977ff7c4a0baf0d5dbb57e235c7

Filter for the account listing request, then follow the HTTP stream on the first matching packet to see the full container list the attacker received: 

Filter: http.request.uri contains "/v1/AUTH_9fb84977ff7c4a0baf0d5dbb57e235c7?format=json"
Follow HTTP stream on first packet...
X-Account-Container-Count: 3
{"name": "dev-files", ...}
{"name": "employee-data", ...}
{"name": "user-data", ...}

Filter: ip.dst == 134.209.71.220 && http.request.uri contains "/v1"
Pkt 16398 — GET .../user-data/user-details.csv HTTP/1.1
UTC Arrival Time: 2025-07-01 ....

09 / persistence

Backdoor Account Creation

With data exfiltrated, the attacker established persistence by creating a new admin user via the Keystone API. Start with a broad filter on the attacker's IP and work down — /identity/v3/users will catch your eye: 

Filter: ip.src == 117.200.21.26
Scan through — /identity/v3/users stands out

Refine: http.request.uri contains "/identity/v3/users"
Several packets with JSON bodies; packet 20839 shows 201 Created
Follow HTTP stream on packet 20776 (contains the POST body)...
{"user": {"password": "P@$$word", "enabled": true,
          "default_project_id": "9fb84977ff7c4a0baf0d5dbb57e235c7",
          "name": "jellibean"}}
HTTP/1.1 201 CREATED
{"user": {"id": "c373da67a62b48f393c45dc071fa80b8", "name": "jellibean", ...}}

Task 14 — What is the MITRE technique ID for the persistence technique in Task 12?

The attacker created an account for persistance.Looking at MITRE ATT&CK, creating a new account in a cloud tenant maps to T1136 with sub-technique .003.
T1136.003 — Create Account: Cloud Account
Takeaway

Key Takeaway

The full attack chain is a textbook cloud intrusion: fuzz → find subdomain → brute-force login → steal the API credential file → enumerate cloud storage → exfiltrate data → create a backdoor account. Every step left artifacts recoverable purely from packet data, no host-level logs required.

Methodology note The OpenStack RC file download is the critical pivot point in this chain — whoever has that file has API-level access to the entire tenant. Monitoring for downloads of *-openrc.sh files (or equivalent credential bundles in other cloud platforms) should be a detection priority. The persistence move (T1136.003) also happened fast: only in a matter of minutes.
