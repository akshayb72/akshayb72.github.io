Vantage

HTB DFIR Sherlocks Medium Jul 2025
01 / overview

What We're Given

Vantage is an HTB Sherlocks DFIR challenge. We're handed two packet captures: controller.xxx.pcap and webserver.xxx.pcap. The scenario is an OpenStack environment — a webserver running a dashboard (Horizon), and a separate controller node running the OpenStack API services. We need to trace an attacker from their initial recon through to persistence.

Environment layout Two captures = two vantage points. The webserver pcap shows what hit the public-facing dashboard. The controller pcap shows the attacker talking directly to the OpenStack REST APIs after they had credentials.
02 / webserver-pcap

Fuzzing and Subdomain Discovery

The first thing the attacker did was fuzz the webserver. Open webserver.xxx.pcap and set filter to http.Then as I go through the packets and when you get to the packet 116.Expand the HTTP layer and look at the User-Agent header — it's not a browser. 

frame.number == 116
GET / HTTP/1.1
Host: dev.vantage.tech
User-Agent: Fuzz Faster U Fool v2.1.0-dev
Accept-Encoding: gzip

Task 1 — What tool did the attacker use to fuzz the web server? (include version)

ffuf@2.1.0

To find the subdomain the attacker discovered, filter webserver.pcap by HTTP only, then sort by packet length descending. Work down the list until you reach packet 21098. The Host header and the Wireshark HTTP object list both show traffic going to a different hostname than the main site. 

Filter: http
Sort by: Length (largest first)
Scroll to packet 21098...
Host: cloud.vantage.tech

Task 2 — Which subdomain did the attacker discover?

cloud
03 / dashboard-login

Brute-Forcing the Dashboard

With the subdomain found, the attacker went after the login page at cloud.vantage.tech/dashboard/auth/login/. Filter the webserver pcap to show only POST requests to that path. 

Filter: http.request.method == "POST" && http.request.uri contains "auth/login"
Pkt 20822 — POST /dashboard/auth/login/  →  302 Found  (fail)
Pkt 20827 — POST /dashboard/auth/login/  →  302 Found  (fail)
Pkt 21091 — POST /dashboard/auth/login/  →  302 Found  (fail)
Pkt 21098 — POST /dashboard/auth/login/  →  200 OK     (success)

Four total POST attempts. Three return a redirect back to the login page (failed auth). The fourth returns 200 — the attacker is in.

Task 3 — How many login attempts did the attacker make before successfully logging in?

3
04 / openrc-download

OpenStack API Config File

After logging in, the attacker grabbed the OpenStack RC file — the credentials bundle that lets you interact with the API from the command line. To find it: go to File → Export Objects → HTTP in Wireshark, sort by size descending, and look for filenames containing openrc. Two packets show up (21256 and 21260). Packet 21260 originates from the attacker's IP (117.200.21.26). Inspect its HTTP response headers. 

HTTP/1.1 200 OK
Date: Tue, 01 Jul 2025 09:40:29 GMT
Content-Disposition: attachment; filename="admin-openrc.sh"
Content-Type: text/plain

Task 4 — When did the attacker download the OpenStack API remote access config file? (UTC)

2025-07-01 09:40:29
05 / controller-pcap

API Enumeration on the Controller Node

Switch to controller.xxx.pcap. The attacker now has an OpenStack RC file and starts hitting the API directly. Filter by the attacker's source IP and HTTP: 

Filter: ip.src == 117.200.21.26 && http
First matching packet: 8490
GET /identity HTTP/1.1
...
UTC Arrival Time: Jul 1, 2025 09:41:44.667723000 UTC

Expand the frame details on packet 8490 and look at the UTC Arrival Time field — this is when the attacker's first API call hit the controller.

Task 5 — When did the attacker first interact with the API on the controller node? (UTC)

2025-07-01 09:41:44

Next, the attacker queried Keystone to find the default project. Filter for requests with projects in the URI and follow the HTTP stream on the relevant packet: 

Filter: ip.src == 117.200.21.26 && http.request.uri contains "projects"
Pkt 20710 — GET /identity/v3/projects?domain_id=default&name=admin
Follow HTTP Stream...
{"id": "9fb84977ff7c4a0baf0d5dbb57e235c7", "name": "admin", "domain_id": "default", ...}

Task 6 — What is the project ID of the default project accessed by the attacker?

9fb84977ff7c4a0baf0d5dbb57e235c7

Task 7 — Which OpenStack service provides authentication and authorization for the OpenStack API?

keystone
The /identity/v3/ path visible throughout the controller pcap is the Keystone API endpoint. OpenStack's auth service is always Keystone — worth filing away for any future cloud DFIR work.
06 / swift

Object Storage Enumeration

The attacker moved to Swift — OpenStack's object storage service (similar to S3). Swift endpoint URLs follow a fixed structure: http://<ip>:8080/v1/AUTH_<project_id>. With the project ID already known, the URL can be constructed and then verified in the pcap. 

Filter: ip.dst == 134.209.71.220 && http.request.uri contains "v1"
GET /v1/AUTH_9fb84977ff7c4a0baf0d5dbb57e235c7?format=json

Task 8 — What is the endpoint URL of the Swift service?

http://134.209.71.220:8080/v1/AUTH_9fb84977ff7c4a0baf0d5dbb57e235c7

Following the HTTP stream on the first ?format=json request shows the full container listing the attacker received: 

Filter: http.request.uri contains "/v1/AUTH_9fb84977ff7c4a0baf0d5dbb57e235c7?format=json"
Follow HTTP Stream on first packet...
X-Account-Container-Count: 3
{"name": "dev-files", ...}
{"name": "employee-data", ...}
{"name": "user-data", ...}

Task 9 — How many containers were discovered by the attacker?

3

The attacker then pulled files from those containers. Filtering for requests under the /v1/ path reveals a GET to user-details.csv. The timestamp comes from that packet's frame details. 

Filter: ip.dst == 134.209.71.220 && http.request.uri contains "/v1"
Pkt 16398 — GET .../user-data/user-details.csv
UTC Arrival Time: 2025-07-01 09:45:23

Task 10 — When did the attacker download the sensitive user data file? (UTC)

2025-07-01 09:45:23
07 / exfiltration

Counting Exfiltrated Records

Export the CSV via File → Export Objects → HTTP, filter by csv, and save user-details.csv. Then count non-blank lines and subtract the header row: 

$ sed '/^[[:space:]]*$/d' user-details.csv | wc -l
29
# 29 lines total — 1 header row = 28 user records

Task 11 — How many user records are in the sensitive user data file?

28
08 / persistence

Backdoor Account Creation

Data exfiltrated, the attacker established persistence by creating a new admin user via the Keystone API. Filter the controller pcap for POST requests to the users endpoint: 

Filter: http.request.uri contains "/identity/v3/users"
Pkt 20776 — POST /identity/v3/users
Follow HTTP Stream...
Request body: {"user": {"password": "P@$$word", "enabled": true,
               "default_project_id": "9fb84977ff7c4a0baf0d5dbb57e235c7",
               "name": "jellibean"}}
---
HTTP/1.1 201 CREATED
{"user": {"id": "c373da67a62b48f393c45dc071fa80b8", "name": "jellibean", ...}}

Task 12 — What is the username of the new user created for persistence?

jellibean

Task 13 — What is the password of the new user?

P@$$word

The attacker then assigned an admin role to the new account via a PUT request, confirming this was a persistence technique — not just a test account. The MITRE mapping is straightforward: creating a new account in a cloud environment to maintain access maps directly to a specific sub-technique under Create Account. 

PUT /identity/v3/projects/9fb84977ff7c4a0baf0d5dbb57e235c7/users/c373da67.../roles/...
HTTP/1.1 204 NO CONTENT  ← role assignment confirmed

Task 14 — What is the MITRE technique ID for the persistence technique in Task 12?

T1136.003 — Create Account: Cloud Account
Takeaway

Key Takeaway

The full attack chain here is a textbook cloud intrusion: fuzz → find subdomain → brute-force login → steal the API credential file → enumerate cloud resources → exfiltrate data → create a backdoor account. Every step left artifacts in the pcap that could be recovered purely from packet data, without host-level logs.

Methodology note In cloud DFIR, the OpenStack RC file download is a critical pivot point — whoever has that file has API-level access to the entire tenant. Monitoring downloads of *-openrc.sh or equivalent credential bundles should be a detection priority. The persistence move (T1136.003) also happened fast: only ~7 minutes elapsed between the RC file download (09:40) and the backdoor account creation (09:48).
